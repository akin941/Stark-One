# WOKWI — simulation as a first-class development environment

Wokwi is where V0 is developed, demonstrated and regression-tested. It is not a
sandbox for throwaway sketches: the simulator runs **the same build artifact** that we
flash to hardware.

---

## 1. Ground rules

1. **One firmware.** `idf.py build` produces the artifact; Wokwi loads it. No separate
   simulator build, no simulator-only sources, no `#ifdef WOKWI` in drivers or apps
   (ADR-0010).
2. **Divergence is documented, not coded around.** Where the simulator does not model a
   signal (panel RST, backlight), firmware still drives it. Where the simulator cannot
   model a peripheral at all (§5), that milestone's verification moves to host tests
   plus hardware tests, and the gap is recorded here.
3. **The diagram is source.** `diagram.json` is reviewed like code; pin changes must
   match `components/stark_board` in the same change.
4. **Every milestone ships at least one CI scenario** that boots the firmware and
   asserts observable behaviour.
5. **Simulate the real SKU.** The board is configured as the ESP32-S3-WROOM-1-**N16R8**
   we will build on (§4), not as whatever default is convenient.
6. **Assert function, never wall-clock time.** Simulated milliseconds are not device
   milliseconds; scenarios assert on ordering, values and counters. Performance gates
   belong to the V1 prototype milestone (ADR-0011, §8).

---

## 2. Toolchain

| Tool | Use | Notes |
| --- | --- | --- |
| Wokwi VS Code extension | Interactive dev loop (F1 → *Wokwi: Start Simulator*) | Reads `wokwi.toml` + `diagram.json` from the repo root |
| `idf.py wokwi` | Command-line simulation from ESP-IDF | Requires ESP-IDF ≥ 6.0 — we are on v6.1; builds first unless `--no-build` |
| `wokwi-cli` | Headless runs and CI | Consumes `--scenario` YAML, streams serial, asserts output |
| `wokwi/wokwi-ci-action` | GitHub Actions | Needs `WOKWI_CLI_TOKEN` as a repository secret |

Wokwi CI runs against a monthly simulation-time quota (free tier ≈ 50 min/month).
Scenarios must therefore be **short**: boot + assert + exit, with an explicit
`--timeout`. Budget ≤ 20 s of simulated wall time per scenario.

## 3. `wokwi.toml` (repo root)

```toml
[wokwi]
version = 1
firmware = 'build/flasher_args.json'
elf      = 'build/stark-one.elf'
# Optional, enabled per-task when the logic analyser is in the diagram:
# vcdFile = 'build/logic.vcd'
```

`flasher_args.json` is generated by `idf.py build` and makes Wokwi load bootloader,
partition table and application exactly as `esptool` would — the closest thing to real
flashing the simulator offers.

## 4. `diagram.json` — V0 circuit specification

Board: `board-esp32-s3-devkitc-1`, configured to match the **physical target SKU**,
ESP32-S3-WROOM-1-**N16R8** — 16 MB flash, 8 MB octal PSRAM:

```json
{
  "type": "board-esp32-s3-devkitc-1",
  "id": "esp",
  "attrs": { "flashSize": "16", "psramSize": "8", "psramType": "octal" }
}
```

The firmware still builds with **PSRAM disabled** (`CONFIG_SPIRAM` off, ADR-0014). That
combination is the point: the simulated silicon is the production SKU, and V0 is
continuously proven to run on it *without* needing PSRAM. When PSRAM is eventually
enabled it is a one-symbol `sdkconfig` change, with no diagram churn and no "it worked
on the 4 MB fiction" surprise.

> **Verify while authoring (STARK-0003):** `flashSize` and `psramSize` are documented
> Wokwi attributes (`"2"|"4"|"8"|"16"|"32"` and `"2"|"4"|"8"` respectively).
> `psramType` is **not** confirmed in Wokwi's public documentation as of September 2026.
> Set it, check that the simulator accepts the diagram without warnings, and then
> record the outcome here: if the attribute is ignored or rejected, drop it, keep
> `psramSize: "8"`, and note explicitly that the simulator models PSRAM size but not
> octal/quad interface mode. Do not leave this ambiguous — the whole value of this
> setting is knowing what is actually being simulated.
>
> **STARK-0003 outcome (2026-09-15):** `psramType: "octal"` is included in `diagram.json`
> but **not verified** in the simulator. `wokwi-cli` is not available in the CI Docker
> image (`espressif/idf:v6.1`), and `idf.py wokwi` requires a GUI. The attribute is
> retained for now to match the physical SKU. When simulator access is available, the
> test is: load `diagram.json` in Wokwi and confirm (a) no warning about unknown
> attribute, and (b) boot proceeds normally. If Wokwi ignores/rejects `psramType`,
> it will be removed and this note updated to state that the simulator models PSRAM
> size (`psramSize: "8"`) but not the octal/quad interface mode.

Parts:

| Part id | Wokwi type | Role |
| --- | --- | --- |
| `esp` | `board-esp32-s3-devkitc-1` | MCU, attrs as above (16 MB flash / 8 MB octal PSRAM) |
| `lcd` | `wokwi-ili9341` | 320×240 SPI panel (no touch variant) |
| `btn_up`, `btn_down`, `btn_left`, `btn_right`, `btn_ok`, `btn_back` | `wokwi-pushbutton` | `attrs: { "color": "grey", "bounce": "1" }` |
| `bz` | `wokwi-buzzer` | Passive buzzer, `attrs: { "volume": "0.1" }` |
| `led` | `wokwi-led` + `wokwi-resistor` (330 Ω) | Status LED on GPIO 18 |
| `la` | `wokwi-logic-analyzer` | **Optional**, added only in tasks that need timing capture |

Connections (matching [HARDWARE.md §2](HARDWARE.md)):

```
esp:12  → lcd:SCK      esp:11  → lcd:MOSI     esp:13  → lcd:MISO
esp:10  → lcd:CS       esp:9   → lcd:DC       esp:3V3 → lcd:VCC     esp:GND → lcd:GND
esp:4   → btn_up:1.l       btn_up:2.l    → esp:GND
esp:5   → btn_down:1.l     btn_down:2.l  → esp:GND
esp:6   → btn_left:1.l     btn_left:2.l  → esp:GND
esp:7   → btn_right:1.l    btn_right:2.l → esp:GND
esp:15  → btn_ok:1.l       btn_ok:2.l    → esp:GND
esp:16  → btn_back:1.l     btn_back:2.l  → esp:GND
esp:17  → bz:1             bz:2          → esp:GND
esp:18  → r1:1             r1:2 → led:A  led:C → esp:GND
```

Notes for the implementer:

* `lcd:RST` and `lcd:LED` are **not simulated** — leave them unconnected in the diagram
  while firmware still drives GPIO 14 and 21. This is intentional (§1.2).
* Wokwi pin labels on the S3 DevKitC-1 board part are the bare GPIO numbers plus
  `3V3`, `5V`, `GND.1/2/3`, `TX`, `RX`, `EN`. Verify the exact label strings the first
  time the diagram is authored (STARK-0003) and fix them once; do not guess repeatedly.
* Lay the buttons out as a D-pad diamond with OK in the centre and BACK to the right,
  so the simulator matches the planned enclosure ([HARDWARE.md §5](HARDWARE.md)).
* Keep `diagram.json` formatted with 2-space indentation and stable key order; it is
  diffed in review.

### 4.1 Later-milestone diagram variants

Additional circuits live beside the root diagram and are selected by copying or by a
`wokwi.toml` per directory:

| File | Milestone | Adds |
| --- | --- | --- |
| `sim/diagram.storage.json` | V0.2 | `wokwi-microsd-card` on SPI2 with CS = GPIO 8 |

## 5. What Wokwi does and does not model

Verified against Wokwi's ESP32 simulation documentation (September 2026):

| Area | Status | Consequence for STARK ONE |
| --- | --- | --- |
| ESP32-S3, GPIO, timers, DMA, dual core | ✅ | V0 fully simulatable |
| SPI, I²C (master), UART, LEDC PWM, ADC, PCNT | ✅ | Display, buttons, buzzer, I²C scanner all testable |
| Flash 2–32 MB, PSRAM 2/4/8 MB, custom partition tables | ✅ | `flashSize: 16` + `psramSize: 8` match the N16R8 target; octal-vs-quad PSRAM *mode* fidelity is unverified (§4) |
| microSD (FAT, ≤ 8 MB, SPI) | ✅ | V0.2 storage testable |
| USB CDC on S3 | ✅ | Console can move to USB later; V0 keeps UART0 |
| Wi-Fi | ✅ (simulated) | Not used in V0 |
| **RMT** | 🟡 transmit-only, LED-strip oriented | **IR (V0.3) is not meaningfully simulatable** — see §5.1 |
| I²S, TWAI | 🟡 partial | Not in the roadmap before V2 |
| **Bluetooth / BLE** | ❌ | Not in the roadmap |
| **MCPWM, ULP, hall sensor, JTAG** | ❌ | Not used |
| NFC reader ICs (PN532 / ST25R) | ❌ no part | V0.4 verified on hardware only |
| Sub-GHz transceivers (CC1101) | ❌ no part | V0.6 verified on hardware only |

### 5.1 Coping with the un-simulatable milestones

For IR, NFC and Sub-GHz the strategy is a three-way split:

1. **Codec / protocol logic → host tests.** NEC/RC5/Sony encode-decode, NDEF parsing,
   OOK/PWM bitstream framing are pure functions over byte arrays. They get thorough
   host unit tests with recorded vectors — which is better coverage than a simulator
   would give anyway.
2. **Driver register sequences → optional custom Wokwi chip.** Wokwi supports custom
   WASM chips; a minimal CC1101 or PN532 register-level stub is a *stretch goal*, not a
   dependency. It would validate SPI/I²C transaction shape, nothing more.
3. **RF/optical behaviour → hardware only,** against our own transmitters and tags,
   with a written bring-up checklist.

Never let a milestone's acceptance criteria depend on simulating something Wokwi does
not model. Where that would happen, the criteria are split into "simulated" and
"hardware-verified" halves explicitly in [TASKS.md](TASKS.md).

## 6. CI scenarios

Scenario files live in `test/scenarios/*.yaml`. Structure:

```yaml
name: v0-boot-and-menu
version: 1
author: STARK ONE
steps:
  - wait-serial: "boot: ui_ready"
  - delay: 200ms
  - set-control: { part-id: btn_down, control: pressed, value: 1 }
  - delay: 60ms
  - set-control: { part-id: btn_down, control: pressed, value: 0 }
  - wait-serial: "menu: sel=1"
  - set-control: { part-id: btn_ok, control: pressed, value: 1 }
  - delay: 60ms
  - set-control: { part-id: btn_ok, control: pressed, value: 0 }
  - wait-serial: "app: start about"
  - set-control: { part-id: btn_back, control: pressed, value: 1 }
  - delay: 60ms
  - set-control: { part-id: btn_back, control: pressed, value: 0 }
  - wait-serial: "app: stop about"
  - expect-pin: { part-id: esp, pin: "18", value: 1 }   # status LED alive
```

This is why UI and app state changes emit terse, stable log lines at INFO level:
**the serial log is the CI assertion surface.** Log-line formats used by scenarios are
part of the public contract of a task and must not be reworded casually; they are
listed in each task's acceptance criteria.

Invocation:

```bash
# local headless
wokwi-cli . --timeout 20000 --scenario test/scenarios/v0-boot-and-menu.yaml

# CI (GitHub Actions)
- uses: wokwi/wokwi-ci-action@v1
  with:
    token: ${{ secrets.WOKWI_CLI_TOKEN }}
    path: /
    timeout: 20000
    scenario: test/scenarios/v0-boot-and-menu.yaml
```

Screenshots: Wokwi can capture the framebuffer in CI (`--screenshot-part lcd
--screenshot-time`), which we use for a coarse visual regression on the root menu. Treat
it as a smoke check, not a pixel-exact golden image — anti-aliasing and timing jitter
make strict comparison brittle.

## 7. Local developer loop

```bash
# one-time
scripts/setup.sh              # verifies ESP-IDF v6.1, installs wokwi-cli

# per change
idf.py build                  # warnings-as-errors
scripts/test_host.sh          # pure-core unit tests (fast, no hardware)
scripts/test_wokwi.sh         # headless scenarios
# or: F1 → "Wokwi: Start Simulator" in VS Code for interactive work
```

Debugging in Wokwi: the simulator exposes a GDB server; `.vscode/launch.json` gains a
configuration pointing at `build/stark-one.elf`. Breakpoints and variable inspection
work, which makes it a legitimate substitute for JTAG during V0 (the S3's JTAG is not
simulated at all).

## 8. Known simulation pitfalls

| Pitfall | Handling |
| --- | --- |
| **Simulated timing is not real timing** | Never assert on any wall-clock quantity — not µs, not ms, not FPS. The simulator does not model SPI wire time, flash latency or cache behaviour, and it runs at the speed of whatever host executes it. Scenarios assert ordering, values and counters; performance is gated at V1 prototype (ADR-0011) |
| Panel RST/backlight unmodelled | Keep driving them; hardware bring-up checklist covers them |
| Button bounce differs from reality | `bounce: 1` in the diagram exercises the debouncer; real bounce is worse — keep the 20 ms filter |
| Serial output can be lost at boot | Assert on a line emitted *after* `stark_log_init()`, never on ROM bootloader text |
| Quota exhaustion | Keep scenarios ≤ 20 s; run the full set on PR, a single smoke test on push |
| Diagram/board pin drift | `scripts/check_pins.py` cross-checks `diagram.json` against the `stark_board` pin map in CI |
